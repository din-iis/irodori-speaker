# irodori-speaker: 朗読に環境音と音楽を重ねる `bgm` ステップ

## Context

irodori-speaker は、小説を Irodori-TTS で読み上げて章ごとの WAV を作るところまでできている（`script` → `synth` の 2 ステップ）。ユーザーの最終目標は「小説から BGM 付きの朗読を自動で作ること」（2026-10-26 表明）であり、本設計はその BGM 部分を足す。

ユーザーは、月は無慈悲な夜の女王、ライ麦畑でつかまえて、葉桜の季節に君を想うということ、のような未読の小説を、散歩・水泳・プラモデル制作の最中に聴く。そのため人手で場面や音を指定する工程を置かず、本文から音の選択と重ね合わせまでを自動で行う。

### ブレインストーミングで決まったこと（ユーザーの決定）

| 項目 | 決定 |
|---|---|
| BGM の目的 | 場面を思い浮かべやすくする。主役は環境音（街の雑踏、雨など） |
| 素材 | 素材ファイルから自動で選ぶ。取得元は Freesound（環境音・音楽とも）。AI による生成は最初の版では行わない |
| 合う音が無いとき | 無音にする（「ずれた音のほうが嫌なので無音でいいです」）。意味が変わらない範囲でのみ広いカテゴリに落とす。見つからなかった場面は一覧に残す |
| 音楽の位置 | 章の頭と場面の切り替わりにだけ流し、声とは重ねない。声の下には環境音だけを流す |
| 収集とタグ付け | すべてツールに任せる（人手の作業なし） |
| 環境音の切り替え頻度 | 大きな場面転換（場所か時間の変化）のときだけ。1 つの音は最低 1 分ほど流す |
| 出力 | 朗読だけの WAV は今のまま残し、BGM 版を別に書き出す。章ごとの MP3 と通しの MP3 |
| 音楽の出入り | いきなり切り替えない。音楽は始まりをフェードイン、終わりをフェードアウトし、環境音とはクロスフェードでつなぐ |

### 私（Claude）の判断で決めたこと

- 3 つ目のサブコマンド `bgm` として `synth` の後に置く。朗読の WAV は読むだけで書き換えない。音量や長さを変えて重ね直すときに、音声合成をやり直さずに済む。
- 最初の版は CLI だけ。WebUI のボタンと `run` への組み込みは対象外とする。
- 声の下の環境音は、声の出入りに合わせて音量を上下させない（ダッキングなし）。もともと声より約 20 dB 小さく流すため、効果が小さいと判断した。
- 音量・音楽の長さ・フェードの秒数は設定項目にし、既定値は下の表のとおりとする。聴いて合わなければ設定で調整する。
- 出力は MP3 にする。防水プレーヤーを含め、再生できる機器が最も多いため。

### Freesound の利用条件（調査済み）

- API の規約（Terms of Use）は「必要な範囲での一時的なコピー」だけを認め、データベースの丸ごとの複製とスクレイピングを禁じている。音ごとのライセンスに従ったクレジット表記が必要。
- 本ツールでは、ダウンロードした音声は重ね終えたら消し、選んだ音の ID とメタデータだけを残す。重ね直すときは選んだ音（1 場面 1 件）だけをダウンロードし直す。クレジットは `CREDITS.txt` に書き出す。
- 試作で取れた音のライセンスは CC0、CC BY、CC BY-NC の 3 種類だった。小説自体に著作権があるので、出力は私的な利用に限り配布しない。この前提なら 3 種類とも使える。
- 回数の上限は標準のキーで 1 分 60 回、1 日 2000 回（https://freesound.org/docs/api/overview.html）。超えると HTTP 429 が返る。試聴用 MP3（`previews`）のダウンロードがこの回数に数えられるかは確認していない。試聴用 MP3 は認証なしで取得できる公開 URL なので、キーを付けずに取りに行く（キーを API 以外のホストに送らないためでもある）。
- 想定する本の大きさは長編 1 冊（10 万〜30 万文字）。最低 400 文字で場面をまとめると場面数はおおむね 250 以下になり、検索は環境音と音楽を合わせて最大でおよそ 500 回である。同じ検索語の結果はキャッシュするので、実際にはこれより少ない。1 冊は 1 日の上限に収まる見込みだが、数冊を続けて処理すると超えうる。
- 参考にした Jamendo は、API の規約 3.3 がキャッシュやオフライン再生を前提にしたアプリを禁じており、この設計と合わないので使わない。

### API キーの扱い（ユーザーと合意済み）

- キーは `~/.config/irodori-speaker/secrets.env`（中身は `FREESOUND_API_KEY=...`、パーミッション 600）にだけ置く。環境変数やシェルの設定ファイルには置かない（AI のエージェントが読めてしまうため）。パスは設定 `bgm.secrets_file` で変えられる。
- キーは HTTP の `Authorization: Token ...` ヘッダーで送り、URL に含めない。画面・ログ・キャッシュのどこにも書かない。例外のメッセージにリクエストのヘッダーが出ないように注意する。
- GPU 機（WSL2）にも同じファイルを、ユーザーが自分の端末で作る必要がある。ファイルが無いか、キーの行が無ければ、`bgm` は作り方を案内して終了コード 2 で止まる。
- Claude Code の `permissions.deny` に `Read(~/.config/irodori-speaker/**)` を入れてある。実装やテストのコードも、このファイルを読まない作りにする（テストは偽の Freesound クライアントを使う）。

## 試作で分かったこと

本設計の音の選び方は、次の 2 回の試作の結果に基づく。どちらもリポジトリの外で行い、コードはリポジトリに入れない（試作 2 の結果とスクリプトは WP0 の材料として `out/bgm-spike/` に退避した）。

### 試作 1: ESC-50 と CLAP（`laion/larger_clap_general`）

5 秒の単発音 2000 件に対し、英語の場面説明で検索した。18 場面のうち 17 場面で 1 位が正しかった（ヘリコプターが飛行機になった 1 件だけが誤り）。一方で、合う音が無い場面 8 件でも何かしらの音が高い点で返り、点数の線引きで「合う音が無い」を判定すると、正解を落とすか誤りを通すかのどちらかになった。CLAP は順位付けには使えるが、採否の判定には使えない。

### 試作 2: Freesound の検索結果と CLAP（9 場面、101 候補）

- 1 位の点数が場面によって大きく違った（波・時計・ピアノは 0.42 前後、公園の鳥は 0.28）。全場面に共通の合格ラインは置けない。
- 的外れな候補（雨の街の検索に混じった電車の音、月面基地の検索に混じった冷蔵庫）は最下位付近に回った。Freesound の検索自体の精度も高く、日本の駅では 12 件すべてが日本の駅の録音だった。
- ユーザーが聴いて確かめた 2 場面では、CLAP の 1 位が外れだった。バーの 1 位「…Pub_Temple_Bar_Ext_Smash_Glass」は屋外でガラスが割れる音で、2 位の「bar chatter」が正しかった。時計の 1 位「Room Tone Workshop Birds Hum Clock Ticking」は鳥と機械のうなりが混じり、3 位の「clock_tick_realistic」が正しかった。どちらも、場面に無い音が名前に書いてあった。CLAP は場面の要素をどれだけ含むかで点を付けるので、余計な音が混じっても点が下がらない。
- 他の 7 場面の 1 位は聴いて確かめていない。
- CLAP に「人の話し声」「音楽」の文を当てて混入を測る方法は使えなかった。「With Music」と名前の付いたバーの録音が、「No_Music」の録音より音楽の点が低かった。
- 1 候補の処理時間は、MP3 全体のデコードが大半を占めていた（10 分の MP3 で 7.7 秒）。採点に使う区間（10 秒 × 最大 6 区間）だけを読むと 0.2 秒になった。CLAP の採点は 6 区間で CPU 0.59 秒、Mac の GPU（MPS）0.15 秒。

これらの結果から、音の選び方を次の順にする。LLM が名前・タグ・説明文を読んで場面に無い音や話し声が入った候補を先に外し、残った候補の中で CLAP の点が高いものを選ぶ。

LLM による候補のふるい分けは、まだ試していない。設計の要になる部分なので、実装の最初の作業で試作 2 の候補を使って確かめる（「実装手順」の WP0）。

## 全体の流れ

```
script.tsv / chapters.json / chapters/NN_*.wav（+ .times.json）
        │
  1. 場面の区切り（LLM） ─────────────→ bgm/scenes.json
  2. Freesound の検索 ──────────────→ bgm/cache/search.json
  3. 候補のふるい分け（LLM）──────────→ bgm/cache/gate.jsonl, bgm/gate.tsv
     LLM を解放する
  4. ダウンロードと CLAP の採点 ───────→ bgm/cache/scores.json
     選んだ結果 ─────────────────────→ bgm/selection.json, bgm/missing.tsv
  5. 重ね合わせと MP3 の書き出し ─────→ bgm/chapters/NN_*.mp3, bgm/<本>_bgm_full.mp3, bgm/CREDITS.txt
```

8GB の GPU に LLM と他のモデルを同時に載せない決まり（CLAUDE.md）を守るため、LLM を使う 1 と 3 を先に済ませ、LLM を解放してから CLAP を読み込む。TTS は `bgm` では読み込まない。LLM の起動・停止と解放は `emotion.py` の `LLMAnnotator` / `LLMServer` と同じ仕組みを使う。

各段の結果はキャッシュし、入力が変わっていなければ再実行で読み直す。途中で止めても、再実行すれば終わった段と場面は飛ばす。

## 1. 場面の区切り

LLM が章の段落を読み、場面の区切りと場面ごとの説明を返す。区切りの単位は段落とする（段落の途中では切り替えない）。

### 入力と出力

- 章を段落の並びとして、`bgm.scene_chunk_chars`（既定 3000 文字）ごとのまとまりに分けて渡す。段落には番号を振る。2 つ目以降のまとまりには、直前の場面の説明を一緒に渡し、「続いているか、新しい場面か」を判断させる。
- 出力は JSON Schema で縛る。場面ごとに次の項目を返す。

| 項目 | 内容 |
|---|---|
| `start_para` | 場面が始まる段落番号 |
| `description` | 英語の短い場面説明（場所・時刻・天気・聞こえる音・雰囲気）。CLAP の採点とふるい分けに使う |
| `ambient_query` | Freesound で環境音を探す英語の検索語（2〜4 語）。場面に流すべき環境音が無い（静かな室内など）ときは `null` |
| `mood` | 場面の雰囲気を表す英語の短い語句（例: `melancholic`, `tense`） |
| `music_query` | 章頭と切り替わりの音楽を探す英語の検索語（2〜4 語） |

- 呼び出し方は `emotion.py` と同じにする。Ollama のネイティブ `/api/chat` に `format`（JSON Schema）・`think`・`keep_alive` を渡し、`openai` 系統では `response_format` を送る。出力は検証し、壊れていれば 1 回だけやり直す。
- やり直しても壊れていたら、そのまとまりは直前の場面が続いているものとして扱う。章の最初のまとまりなら、環境音も音楽も無い場面とする。このときは `missing.tsv` に理由 `llm_error` で残す。

### 最低 1 分の扱い

1 つの場面が `bgm.min_scene_chars`（既定 400 文字。朗読でおよそ 1 分）より短ければ、前の場面にまとめる。章の最初の場面が短ければ次の場面にまとめる。音を探す前にまとめるので、使わない場面の音を探さずに済む。

### 結果の保存

- `bgm/scenes.json` に章ごとの場面の並び（開始・終了の段落、上の各項目）を書く。
- LLM の応答は `bgm/cache/scenes.jsonl` にキャッシュする。キーはモデル名・まとまりの本文・直前の場面の説明・`think`・プロンプトの版。

## 2. Freesound の検索

- `GET https://freesound.org/apiv2/search/` に検索語、`filter`（長さ）、`fields`、`page_size` を渡す。`fields` は `id,name,tags,description,duration,license,previews,username,url`。試作では名前とタグしか取らなかったが、説明文はふるい分けの手がかりになるので取る。
- 長さの条件は、環境音が `bgm.ambient_duration`（既定 `[30 TO 900]` 秒）、音楽が `bgm.music_duration`（既定 `[30 TO 300]` 秒）。音楽は章頭で使う長さ（フェードを含めて 25 秒）より長いものに限る。
- 候補数は `bgm.candidates`（既定 12）。
- 同じ検索語と条件の結果は `bgm/cache/search.json` にキャッシュする（本ごと）。
- HTTP 429 のときは、応答の `detail` が 1 日の上限（day）を指していれば、その場で `bgm` 全体を止める。止める前に、それまでの検索・ふるい分け・採点の結果はキャッシュに書いてあるので、翌日に同じコマンドを実行すれば続きから進む。止めるときは「1 日の上限に達したので、明日もう一度実行してください」と案内し、章の MP3 は書かない（無音の場面だらけの MP3 を作らないため）。
- 1 分の上限による 429 は、`Retry-After` があればその秒数（ただし 120 秒まで）、無ければ 60 秒待ってやり直す（最大 3 回）。`detail` で区別できないときも、`Retry-After` が 120 秒を超えれば 1 日の上限として扱う。
- それ以外の失敗や通信の失敗では、その場面を `missing.tsv` に理由 `error` で残し、キャッシュしない（次の実行でやり直す）。
- 1 分 60 回を超えないよう、API の呼び出しの間隔を 1 秒以上空ける。

## 3. 候補のふるい分け

LLM に場面の説明と候補の一覧（ID、名前、タグ、説明文の先頭 300 文字）を渡し、候補ごとに採否と理由を返させる。場面ごとに 1 回呼ぶ。

環境音の候補は、次のどれかに当たれば外す。

- 場面に無い音が名前・タグ・説明文に書いてある（試作のガラスが割れる音、鳥と機械のうなり）。
- 聞き取れる話し声が入っている（アナウンス、会話、ラジオ、朗読）。ただし、バーや雑踏のように、言葉の聞き取れない人のざわめきが場面の一部であるものは外さない。
- 音楽が入っている（「with music」など）。
- 場面と場所・時代・天気が食い違う。

音楽の候補は、歌や話し声が入っているもの、効果音、場面の雰囲気と食い違うものを外す。

- 迷ったときは外す（ユーザーの「ずれた音より無音」に合わせる）。
- 結果は `bgm/cache/gate.jsonl`（キー: モデル名・場面の説明・候補 ID・プロンプトの版）にキャッシュし、人が読める形で `bgm/gate.tsv`（章、場面、候補 ID、名前、採否、理由）にも書く。外し方が厳しすぎるか緩すぎるかを、この表で調べる。
- LLM の出力が壊れていたら 1 回だけやり直し、それでも壊れていれば、その場面の候補はすべて外す。

## 4. ダウンロードと CLAP の採点

- ふるい分けで残った候補だけ、試聴用 MP3（`preview-hq-mp3`）をダウンロードする。ダウンロードは並行で行う（既定 6 本）。
- 採点の方法は試作 2 と同じ。音声を 10 秒の区間に分け、最大 6 区間（等間隔）だけを読み込んで CLAP の音声埋め込みを作り、`"the sound of " + description` の文の埋め込みとのコサイン類似度の平均を点とする。全体をデコードしない。
- 場面の中で点が最も高い候補を選ぶ。合格ラインの点数は置かない。
- 残った候補が 0 件なら、その場面は無音にし、`missing.tsv` に理由 `no_result`（検索結果が 0 件）か `all_rejected`（すべて外した）で残す。
- 点は `bgm/cache/scores.json` にキャッシュする（キー: 候補 ID・場面の説明・CLAP のモデル）。
- 選んだ結果は `bgm/selection.json` に書く。場面ごとに、選んだ音の ID・名前・作者・URL・ライセンス・長さ・点と、音楽の ID を持つ。
- CLAP のモデルは `bgm.clap_model`（既定 `laion/larger_clap_general`）、デバイスは `bgm.device`（既定 `cuda`、Mac では `mps`）。

### 音楽の選び方

- 章頭の音楽は、その章の最初の場面の `music_query` と `mood` で選ぶ。
- 場面の切り替わりの音楽は、次の場面の `music_query` と `mood` で選ぶ。
- 選び方は環境音と同じ（検索 → ふるい分け → CLAP の順位）。CLAP の文は `"a " + mood + " piece of music"` とする。
- 同じ検索語の音楽は、同じ章の中で使い回してよい。

## 5. 重ね合わせ

### 段落の時刻

場面の区切りを時刻に直すため、`synth` の `assemble.write_chapter` を変更し、章の WAV と同時に `NN_タイトル.times.json` を書かせる。中身はサンプリングレート、全体のサンプル数、段落ごとの開始・終了サンプル位置。章の WAV と同じく一時ファイル経由で書く。

`bgm` は、`.times.json` が無いか、そのサンプル数が章の WAV と一致しない章があれば、`synth --chapters N` の再実行を案内して止まる。文ごとのキャッシュがあるので、再実行で音声合成はやり直さない（TTS のモデルは読み込む）。

### 時間の並び

BGM 版の章は、朗読の WAV の途中に音楽の区間を差し込んで作る。そのため BGM 版は朗読だけの版より長くなる。

```
[章頭の音楽 intro] [場面1の朗読 + 環境音] [切り替わりの音楽 bridge] [場面2の朗読 + 環境音] ...
```

- 章頭: 無音から音楽をフェードインし（`music_fade_in` 2 秒）、`intro_seconds`（20 秒）流してフェードアウトする（`music_fade_out` 3 秒）。フェードアウトの間に最初の場面の環境音をフェードインし、音楽が終わってから朗読を始める。
- 場面の切り替わり: 前の場面の最後の段落が終わった位置に `bridge_seconds`（8 秒）の区間を差し込む。前の場面の環境音をフェードアウトしながら音楽をフェードインし（重ねる長さは `ambient_crossfade` 4 秒）、音楽をフェードアウトしながら次の場面の環境音をフェードインして、音楽が終わってから朗読に戻る。
- 音楽が見つからない切り替わりでは区間を差し込まず、環境音どうしを `ambient_crossfade` でクロスフェードする。章頭の音楽が見つからなければ intro を差し込まない。長い無音を作らないためである。
- 素材の途中で音楽を切る場合も、必ずフェードアウトしてから終える。
- 章の終わりでは、環境音を朗読の終わりから 3 秒でフェードアウトする。

### 環境音のループと音量

- 場面より短い環境音は、つなぎ目を 2 秒のクロスフェードにしてループさせる。素材の冒頭と末尾にある無音やフェードは、ループの前に削る。
- 音量は、朗読の音声のある部分の RMS を基準に、環境音を `ambient_db`（既定 −20 dB）、音楽を `music_db`（既定 −3 dB）に合わせる。素材の RMS は素材全体で測る。重ねた結果がクリップしないよう、最後にピークを −1 dBFS に抑える。
- 朗読の WAV はモノラル、試聴用 MP3 はステレオ 44.1 kHz である。出力はステレオにし、朗読は中央に置く。素材は章の WAV のサンプリングレートに合わせて変換する。

### 書き出し

- 章ごとに `bgm/chapters/NN_タイトル.mp3` を ffmpeg で書く（`bgm.mp3_bitrate` 既定 `192k`）。一時ファイルに書いてから置き換える。
- 全章の BGM 版が揃っていれば、`bgm/<本>_bgm_full.mp3` を作る。
- 章ごとに署名（`.sig`）を持つ。署名には、朗読の章 WAV の署名、その章の `selection.json` の内容、重ね合わせの設定値を入れる。一致すれば重ね直さない。
- 重ね終えたら、ダウンロードした音声を消す。重ね直すときは、`selection.json` の ID で選んだ音だけをダウンロードし直す。
- `bgm/CREDITS.txt` に、使った音ごとに題名・作者・URL・ライセンスを書く。

### `missing.tsv`

列は `chapter, scene, start_para, kind, description, query, reason`。`kind` は `ambient` / `intro` / `bridge`、`reason` は `no_result` / `all_rejected` / `llm_error` / `error`。`ambient_query` が `null`（意図して無音）の場面は書かない。

## 外れた音を直す方法

`scenes.json` と `selection.json` は入力とキャッシュから作り直す派生ファイルとし、手で直すことは想定しない（`script.tsv` の「手直しが正」の原則は適用しない）。ユーザーは小説を読んでいないまま聴くので、場面の説明を手で直す運用はとらない。

聴いて「この音は違う」と気づいたときのために、除外リスト `out/<本>/bgm/exclude.txt` だけを手で書けるファイルとして用意する。

- 1 行に 1 つ Freesound の ID を書く（`#` 以降はコメント）。`CREDITS.txt` に ID と題名が載っているので、そこから写せる。
- 次の `bgm` の実行で、除外した ID を選んでいた場面だけ、ふるい分けで残った候補の次点を選び直す。次点が無ければ無音にし、`missing.tsv` に理由 `all_rejected` で残す。
- 除外した ID は、同じ本の他の場面でも選ばない。
- `bgm` はこのファイルを読むだけで書き換えない。

## 設定（config.example.yaml に足す節）

```yaml
bgm:
  secrets_file: ~/.config/irodori-speaker/secrets.env   # FREESOUND_API_KEY=... の 1 行（chmod 600）
  clap_model: laion/larger_clap_general
  device: cuda              # cuda | mps | cpu（CLAP）
  candidates: 12            # 1 回の検索で取る候補数
  ambient_duration: "[30 TO 900]"
  music_duration: "[30 TO 300]"
  scene_chunk_chars: 3000   # LLM に一度に渡す本文の量
  min_scene_chars: 400      # これより短い場面は前の場面にまとめる（朗読でおよそ 1 分）
  download_workers: 6
  ambient_db: -20.0         # 朗読に対する環境音の音量
  music_db: -3.0            # 朗読に対する音楽の音量
  intro_seconds: 20.0
  bridge_seconds: 8.0
  music_fade_in: 2.0
  music_fade_out: 3.0
  ambient_crossfade: 4.0
  mp3_bitrate: 192k
```

LLM は既存の `llm` 節の設定をそのまま使う。

## コマンド

```bash
uv run --no-sync python -m irodori_speaker bgm novel.txt -c config.yaml
```

- オプションは `--chapters`（対象の章）、`--replan`（`scenes.json` と場面の LLM キャッシュを捨てて場面を区切り直す。場面の説明が変わるので、以後のふるい分けと採点もやり直しになる）、`--llm-model`、`--think`。
- 特定の音を替えたいときは、オプションではなく除外リスト（上の節）を使う。同じキャッシュから選び直しても同じ音が選ばれるので、`--reselect` のようなオプションは設けない。
- 前提: `synth` で章の WAV と `.times.json` ができていること。
- `run` には組み込まない。

## モジュール構成

| モジュール | 役割 |
|---|---|
| `bgm_scenes.py` | 場面の区切り（LLM の呼び出し、検証、最低文字数でのまとめ、キャッシュ） |
| `freesound.py` | キーの読み込み、検索、ダウンロード、429 の待機。キーを外に出さない |
| `bgm_select.py` | ふるい分け（LLM）、CLAP の採点、選択、`selection.json` / `missing.tsv` / `gate.tsv` |
| `bgm_mix.py` | 時間の並び、ループ、フェード、音量、MP3 の書き出し、`CREDITS.txt` |
| `pipeline.py` | `build_bgm`（上の 3 つを順に呼び、LLM の解放を挟む） |
| `assemble.py` | `write_chapter` が `.times.json` も書く |
| `cli.py` | `bgm` サブコマンド |

- torch と transformers は `bgm_select.py` の関数の中で読み込む（`synth.py` と同じ。Mac のテストを壊さないため）。
- `pyproject.toml` に extra `bgm = ["transformers"]` を足す。torch は `tts` / `cu128` の extra のものを使う。MP3 のデコードは soundfile（libsndfile 1.1 以降は MP3 を読める。試作で区間の読み込みを確認済み）、変換は torchaudio、書き出しは ffmpeg を使う。
- LLM、Freesound、CLAP はそれぞれ差し替えられる形（引数で渡すクラス）にし、テストでは偽物を使う。

### WP0: ふるい分けの確認

- 材料: 試作 2 の結果とスクリプトを `out/bgm-spike/`（git に入れない）に退避してある。`results.tsv` は 9 場面 101 候補の名前・タグ・CLAP の点を持つ。
- 本番と同じく説明文も渡して試すため、使い捨てのスクリプトで 9 場面を Freesound で検索し直し（説明文を取る）、GPU 機の Ollama（既定の `qwen3.5:4b-q8_0`）でふるい分けて、候補ごとの採否と理由を TSV に書く。Freesound のキーを使うので、ユーザーが GPU 機の自分の端末で実行し、コーディネーターは TSV だけを読む。検索結果が試作 2 と変わっていてもよい（判定に使う ID は下の 6 件で、検索結果に含まれなければ個別に取得する）。
- 合格の条件:
  - 外れと確かめた 760742（バー、屋外でガラスが割れる）と 520467（時計、鳥と機械のうなり）を外す。
  - 正解と確かめた 543913（bar chatter）と 62850（clock_tick_realistic）を残す。
  - 名前で音楽や話し声の混入が分かる 729329・729330（With Music）と 361913（Announcements）を外す。
  - 9 場面のすべてで、少なくとも 1 件が残る。
- 合格しなければプロンプトを直して再試行する。2 回直しても合格しなければ、ユーザーと設計を見直す。

実装はワークツリーごとの Sonnet のワーカーに任せ、コーディネーターが指示書・確認・レビューを行う（これまでと同じ運用）。

## 検証

- Mac のテスト（`uv run pytest -q`）: 場面の検証とまとめ、ふるい分けの結果の扱い、`missing.tsv` の理由、キャッシュの再利用、時間の並び（intro・bridge・フェードの位置）、ループのつなぎ目、音量の計算、署名の一致を、偽の LLM・Freesound・CLAP と合成した WAV で確かめる。MP3 の書き出しは ffmpeg があるときだけ試す。
- GPU 機での確認: 短い章（数場面）で `bgm` を通し、ユーザーが聴いて、場面と音が合っているか、音楽の出入りが滑らかか、環境音の音量が朗読の邪魔にならないかを判断する。
- Freesound のキーを使う実行は、ユーザーが自分の端末で行う。
